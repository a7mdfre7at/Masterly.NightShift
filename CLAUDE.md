# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Masterly.NightShift started from the source of an earlier open-source library (see `NOTICE.md`) and was renamed throughout. Existing data keeps working: the SQL Server schema is still named `HangFire`, the drain-mode storage key is still `hangfire:control`, and `TypeHelper` maps type names stored by the earlier library (`Hangfire.*, Hangfire.Core`) to the new types. Files that carry a license header naming the earlier project must keep it (`NOTICE.md`). Everything written for this project is MIT (`LICENSE.txt`). The packages declare `MIT AND LGPL-3.0-or-later` and carry `LICENSE-LGPL-3.0.txt` and `LICENSE-GPL-3.0.txt`.

Masterly.NightShift is a .NET library for fire-and-forget, delayed, recurring, and continuation background jobs, persisted to pluggable storage. This repo ships the NuGet packages `Masterly.NightShift.Core`, `Masterly.NightShift.SqlServer`, `Masterly.NightShift.EntityFrameworkCore`, `Masterly.NightShift.Redis`, `Masterly.NightShift.MongoDB`, `Masterly.NightShift.InMemory`, `Masterly.NightShift.NetCore`, `Masterly.NightShift.AspNetCore`, and the `Masterly.NightShift` meta-package (`src/Masterly.NightShift`, which installs Core, SqlServer and AspNetCore only). It targets .NET 8 and later only (`net8.0;net10.0`); third-party storages implement its storage contract, so **binary/API compatibility of the public API and the storage interfaces is a primary constraint**.

## Build and test

Everything builds and packs with the dotnet CLI; package metadata (authors, license, icon, readme, version) lives in `src/Directory.Build.props`, and each package's description in its `.csproj`. `Masterly.NightShift.Core` packs the source generator as an analyzer and `build/Masterly.NightShift.Core.props`. Cronos and Dapper are normal package dependencies (they are no longer merged into the assemblies).

```
dotnet build Masterly.NightShift.slnx -c Release
dotnet pack src/Masterly.NightShift.Core -c Release --no-build -o artifacts   # likewise SqlServer, InMemory, Redis, MongoDB, EntityFrameworkCore, NetCore, AspNetCore, and src/Masterly.NightShift (meta-package)
```

Run the build and the tests on `net8.0` and `net10.0` before proposing a pull request.

Day-to-day with the dotnet CLI:

```
dotnet build Masterly.NightShift.slnx -c Release
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0 --filter "FullyQualifiedName~Masterly.NightShift.Core.Tests.Server.WorkerFacts"
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0 --filter "FullyQualifiedName~WorkerFacts.Execute_TakesConnectionAndReleasesIt"
```

- Test projects target `net8.0;net10.0`. Use `-f` to pick one. `tests/Masterly.NightShift.Core.Tests`, `tests/Masterly.NightShift.SqlServer.Tests` and one project per other storage (`InMemory`, `Redis`, `MongoDB`, `EntityFrameworkCore`) test their packages; `tests/Masterly.NightShift.AspNetCore.Tests` tests `Masterly.NightShift.NetCore` and `Masterly.NightShift.AspNetCore` together (DI registration, hosted services, endpoint mapping, keep-alive). Building requires the .NET 10 SDK (pinned in `global.json`).

- Package versions are managed centrally in `Directory.Packages.props`; `PackageReference` items have no `Version`. Library dependencies are kept current (`dotnet list Masterly.NightShift.slnx package --outdated`); raising one raises the minimum consumers get. Exceptions: `Microsoft.CodeAnalysis.CSharp` stays at the oldest Roslyn the generators need (see the comment there); the Microsoft.Extensions packages of `Masterly.NightShift.NetCore` stay at the oldest serviced version for each target framework (8.0.x on `net8.0`, 10.0.x on `net10.0`), so apps keep their runtime's stack; the source-only packages (LibLog, StackTraceParser/Formatter, MoreLinq) are references with `ExcludeAssets="contentFiles"`: the code compiled is the vendored copy, so bumping them changes nothing; and `Masterly.NightShift.SqlServer` references a patched `System.Security.Cryptography.Pkcs` because `Microsoft.Data.SqlClient` 7.1.2 still asks for a vulnerable one (drop it when the client is fixed).

- **The public API has no baseline yet.** Nothing has been published under the `Masterly.NightShift.*` IDs. `dotnet pack` runs package validation, which checks that the API agrees across target frameworks. Until 1.0.0 ships, its CHANGELOG section describes what the release offers, grouped by area, with absolute links to the site (it is the GitHub Release body). Work on 1.0.0 updates that description where a feature belongs and never appends change entries ("no longer", "instead of", "is gone", review or fix logs), because there is no earlier version to change from. How 1.0.0 was built is kept in `docs/architecture/release-1.0.0-development-log.md`.
- `benchmarks/Masterly.NightShift.Benchmarks` compares NightShift with Hangfire from NuGet (BenchmarkDotNet, plus `throughput <jobs> <rounds> <workers> [callers]` for an end-to-end run; `NS_DD=1` turns on `AllowDelayedDurability`, `BENCH_ONLY=NightShift` skips Hangfire). It stays out of the solution and off the central package list, so Hangfire never reaches CI or the packages. `docs/benchmarks.md` publishes its results, with a summary table in `README.md` and `docs/README.md` (the same rows) and the ratios in `docs/compared-with-hangfire.md`: re-run it on a quiet machine and update all four when the job pipeline, serialization or the SQL Server storage changes. Run the end-to-end part against a full SQL Server (the user decided on 2026-11-10: not LocalDB, which is the Express engine and gave misleading results); set `NightShift_SqlServer_ConnectionStringTemplate`.

### Test prerequisites

- **SQL Server tests** need a reachable SQL Server. Set `NightShift_SqlServer_ConnectionStringTemplate` to a connection string with a `{0}` database placeholder, for example `Server=.\sqlexpress;Database={0};Integrated Security=True;TrustServerCertificate=True;` or, with LocalDB, `Server=(localdb)\MSSQLLocalDB;Database={0};Integrated Security=True;TrustServerCertificate=True;`. The default is `Server=.\;Database={0};Trusted_Connection=True;...`. Each TFM uses its own database (`Masterly.NightShift.SqlServer.Tests.net8_0`, and so on), created on demand with a case-sensitive collation. To override the name, set `NightShift_SqlServer_DatabaseName`. The EF Core tests on SQL Server use databases of their own (`EfTestDatabases`): `Masterly.NightShift.EntityFrameworkCore.Tests.{name}.v{schema version}.{tfm}`, or, with `NightShift_SqlServer_DatabaseName` set, that name followed by `.EntityFrameworkCore.{name}...`, so runs given different names never share a database.
- **Redis tests** need `NightShift_Redis_Configuration` (a StackExchange.Redis configuration string, such as `localhost:6379`) and **MongoDB tests** need `NightShift_Mongo_ConnectionString` to a replica set (`mongodb://localhost:27017/?replicaSet=rs0&directConnection=true`; a single `mongod --replSet rs0` after `rs.initiate()` will do). Without them, those tests are skipped. Each test uses its own key prefix or collection prefix and removes them afterwards. The EF Core tests run on SQLite files and, with `NightShift_SqlServer_ConnectionStringTemplate`, on SQL Server.
- **The storage conformance suite** (`tests/Shared/StorageConformance/StorageConformanceFacts.cs`) is compiled into every storage's test project, SQL Server's included (`SqlServerConformanceFacts`). A change to storage behavior goes there first, so every storage is held to it.
- Test projects use `extern alias ReferencedCronos` (see the `ChangeAliasesOfStrongNameAssemblies` target) so tests can reference Cronos without clashing with the copy the library uses.

## Architecture

### Source layout

Files are grouped by feature, and **namespaces don't follow folders**: most public types stay in `Masterly.NightShift` (or `Masterly.NightShift.Client`, `.Server`, `.States`, `.Storage`, `.Dashboard`...) wherever the file lives, so moving a file never breaks the API. Put a new file in the folder of its feature, keep the namespace the API needs, and put its tests in the same folder of the test project.

- `Masterly.NightShift.Core`: `Jobs/` (creating jobs, continuations, fan-in, batches, tags, notes, catalog), `RecurringJobs/`, `Scheduling/` (CRON helpers, `TimeText`), `Hosting/` (`BackgroundJobServer`, options, drain mode, activator, cancellation), `Filters/` (`Retries/`, `Concurrency/`, `Timing/`, `Behavior/`, plus the global collections), `Monitoring/` (alerts, audit log, activity feed, insights), `Configuration/` (`GlobalConfiguration` and its extensions). The infrastructure folders `Client/`, `Server/`, `States/`, `Storage/`, `Processing/`, `Dashboard/`, `Diagnostics/`, `Common/` and `Profiling/` match their namespaces. `Logging/` holds `LateBoundLogProvider`, which makes every logger follow the provider set later with `UseLogProvider` (installed by a module initializer). Vendored code is in `App_Packages/`.
- `Masterly.NightShift.SqlServer`: the storage, connection, transaction and monitoring classes at the root; `Queues/`, `Locking/`, `Maintenance/`, `Schema/` and `Infrastructure/`.
- `Masterly.NightShift.InMemory`, `.Redis`, `.MongoDB`, `.EntityFrameworkCore`: the other storages. They use only Core's public API, as a third-party storage would, and share internal code in `src/Shared/Storage` (compiled into each with `<Compile Include>`, not a project): `RecordingTransaction` records a transaction's writes as `StorageOperation`s and hands them to the storage's `Apply`, `SharedMonitoringApi` builds the dashboard's lists from a few queries, `LeaseLock`/`ReentrantLocks` are the distributed locks, and `FetchedJobBase` keeps a fetched job invisible with a timer and puts it back when disposed unacknowledged. Job ids are numbers on every storage. The EF Core storage reads the database's clock through `EfDatabaseClock`: built-in statements for SQL Server, PostgreSQL, MySQL/MariaDB and Oracle, `EntityFrameworkCoreStorageOptions.DatabaseClockSql` for any other provider, and `JobClock` on SQLite, whose clock is the process's. `HasFeature(Connection.GetUtcDateTime)` answers from the configuration alone and never asks the database. A failed read is never final: SQL Server's statement (`Verified: true`) is never given up on, its failures surface as storage errors; any other statement (`Verified: false`, because only SQL Server's statement and the SQLite path run in this repository's tests) is taken for wrong only after 3 refusals by a reachable database over at least 5 seconds, or at once for an answer that isn't a time or is more than 30 minutes from the process clock. It is then asked again every 15 seconds while the process uses `JobClock`, and taken up when it answers. A process switches clocks at most once per storage, from its own to the database's, never back. Server heartbeats are written and timed out with the storage's clock on EF Core and MongoDB, as on SQL Server and Redis. EF Core staging (`NightShiftStaging.cs`) routes the client's reads and writes about what the context staged in its open transaction (or `TransactionScope`) through an `EfConnection` created `within` that transaction, on the application's connection; locks, the id reservation and everything else stay on the storage's own connections. Chains can't be staged. A staged continuation or join of parents the context didn't stage is registered on them only after the commit (re-elected through the storage; the set `staging:continuations` and `StagedContinuationsProcess` cover a process that stops in between). A `[PreventDuplicates]` fingerprint reservation commits at once, outside the application's transaction: staging recognises Core's fingerprint records by their `fingerprint:` key, so a change to that format needs the EF Core tests. After each successful save the staging subscription detaches the storage's rows from the context. The storage's own contexts always track queries and detect changes (`CreateContext`), whatever the application's factory set, and staging in the application's context switches tracking on only while it writes the storage's rows. Tables are created with `SchemaVersion` first, so a process that finds it without a version row waits for, or completes, a creation in progress. The expiration manager deletes the expired `Job` rows first, the expiry checked in the same statement, and lets cascading foreign keys take their states and parameters; where they don't cascade it deletes children first in one transaction that locks the jobs still expired. With a retrying execution strategy, each storage transaction writes a marker field in the hash `ef-storage:commits` (5 minutes, deleted every minute) that the verify of `ExecuteInTransaction` looks for, so a commit whose reply was lost isn't applied twice. Operations borrowed into the application's transaction run without retries (`NestedExecution`), so `EnableRetryOnFailure` works. Fetching reads `JobQueue` with `readpast` on SQL Server, so a staged entry in an open transaction never blocks workers. On EF Core, lock leases (`EfConnection`, `ILeaseStore`) and fetch invisibility use the database's clock too, invisibility from `EfDatabaseClock.ApproximateUtcNow` (a reading at most 1 second old); row expiry and state timestamps still use `JobClock`. The in-memory storage judges leases and fetch invisibility by `Stopwatch`, not `JobClock`, so a test that moves its clock never hands a held lock or a running job to a second owner.
- `Masterly.NightShift.NetCore`: `DependencyInjection/`, `Hosting/` and `AspNetCore/`.
- `Masterly.NightShift.AspNetCore`: dashboard middleware and endpoint mapping at the root, `Dashboard/` (ASP.NET Core adapters) and `HealthChecks/` (`AddNightShift` for `IHealthChecksBuilder`).
- Embedded resources are named after their path, so the dashboard's `Content/` stays where it is, and `Schema/Install.sql` keeps its old name through `LogicalName`.

User documentation is in `docs/` (start at `docs/README.md`); design notes are in `docs/architecture/`.

### Job lifecycle (Masterly.NightShift.Core)

1. **Client side** (`Client/`, `BackgroundJobClient`, `BackgroundJob` static facade, `RecurringJobManager`): a lambda expression is turned into a `Common.Job` (type + method + args). `Storage.InvocationData` serializes it. `IBackgroundJobFactory` → `CoreBackgroundJobFactory` creates it in storage, running client filters (`IClientFilter`) around creation.
2. **State machine** (`States/`): every transition goes through `IBackgroundJobStateChanger` → `StateMachine`/`CoreStateMachine`. Election filters (`IElectStateFilter`) can redirect the candidate state, which is how `AutomaticRetryAttribute` turns `Failed` into `Scheduled`. Apply filters (`IApplyStateFilter`) and `IStateHandler`s (`GlobalStateHandlers`) then perform the storage side effects inside one `IWriteOnlyTransaction`. Built-in states: Enqueued, Scheduled, Processing, Succeeded, Failed, Deleted, Awaiting (continuations). Work that must wait until the transaction is committed, such as raising an alert, goes through the internal `ApplyStateContext.RunAfterCommit` / `ElectStateContext.RunAfterCommit`: `BackgroundJobStateChanger` runs it after `Commit()` and drops it when the commit fails, so a retried state change doesn't do it twice. Work about something a filter already committed on its own (the circuit breaker's `CircuitOpened` alert) uses `ElectStateContext.RunAfterCommitAttempt`, which runs after the job's lock is released whether the commit worked or not. `CoreStateMachine` expires the job when `ApplyStateContext.JobExpires` (the new state is final, or a filter set the internal `ExpireInNonFinalState`, as failed-job retention does) and persists it otherwise; code that ties data to the job's lifetime (`JobConsoleStateFilter`) checks `JobExpires`, not `IsFinal`. An election filter can say "not now, look again in a moment" about a job a worker is about to process: the worker passes a `JobLookAgain` (`States/JobLookAgain.cs`, `StateChangeContext.LookAgain`) with the state change to Processing, and the internal `ElectStateContext.TryLookAgain(pause)` has `BackgroundJobStateChanger` drop its transaction, so nothing is stored (no state, no history, no parameter), release the job's lock and return `null`. The worker keeps the fetched job (still Enqueued and invisible, not back in its queue), waits for the pause and repeats the state change; it calls `IFetchedJob.Requeue()` only if the server stops meanwhile (3 attempts). It is offered to the first election filter only (`StateMachine` withdraws it afterwards, so no later filter has acted on a state change that didn't happen), never with a caller's transaction or with filters disabled, and only while the pool can afford it: `Server/WorkerWaits.cs`, one per `Worker` (so per pool), allows 5 seconds per job and 2 seconds in any 10 of time when no worker of the pool is fetching, by `Stopwatch`. `JobChainStepFilter`, registered first, is its only user. The internal `ElectStateContext.ReplaceCandidateState` sets the candidate without adding the replaced one to `TraversedStates`, for a job that never was a candidate for that state (a step put back instead of processed has no Processing entry in its history).
3. **Server side** (`Server/`, `Processing/`): `BackgroundJobServer` builds the list of processes: `Worker` (pool of `WorkerCount` threads), `DelayedJobScheduler`, `RecurringJobScheduler`, `ServerHeartbeatProcess`, `ServerWatchdog`, plus any storage-provided processes. It hands them to `BackgroundProcessingServer`, which runs them through `Processing/BackgroundDispatcher` + `BackgroundExecution` (retry/backoff loop). `Worker` fetches a job, moves it to Processing, calls `IBackgroundJobPerformer` (server filters `IServerFilter` wrap `CoreBackgroundJobPerformer`), then moves it to Succeeded/Failed. The server's worker pools are wrapped in `GatedWorker` and ask `Server/WorkerGate.cs` before each fetch. The gate is closed while the server is paused by hand (read from the drain-mode cache) and, with `UseDeploymentFencing`, while it is fenced and until a check of `DeploymentFencingProcess` has decided for the server's current id: a server that gets a new id (heartbeat found it removed, or timed out) is undecided again, because the fencing pause is on the old id. So paused and fenced servers don't fetch; `DrainModeFilter` holds the one job a worker that was already waiting still gets, and `Server/ServerHold.cs` keeps that hold's time in the `ServerHold` job parameter so `PerformContext.Lateness` leaves it out (holds by the global switch or a paused queue still count). A check that finds the server fenced closes the gate before it writes anything. A decision that the server may work expires (see below): the gate then closes, with one warning, until a check succeeds. `DeploymentFencingProcess.Check` is serialized by a lock, and a check for a server id that was given up (the `givenUp` token: stop, or restart with a new id) neither pauses that id nor decides the gate. `ServerHold` keeps a list of holds (`start-end;start~latest`, the last 16), ended by any state that follows the hold and never counted past `latest`, the held state's `EnqueueAt` plus `ServerHold.PollingAllowance` (15 seconds, the default schedule polling interval: the scheduler moves a job with a queue of its own without a state change, which nothing notes); only held time after the job's anchor comes off its lateness. A check that can't take `lock:nightshift:deployment` within `DeploymentFencing.LockTimeout` (15 seconds) changes nothing: no takeover is written without that lock, so the gate's last decision is confirmed (`WorkerGate.Confirm`), one warning is logged and the check is retried within a second. The gate's "may work" decision therefore expires after `TakeOverAfter` + `LockTimeout` since the last check that decided, took the lock or timed out on it; only real storage errors run it out. A server takes back its own pause in `BackgroundServerProcess` when it stops or gets a new id. A `Worker` passed as an additional process isn't gated. Deployment ids are compared without regard to case (`DeploymentFencing.IsSame`), and their fields are named in lower case.
4. **Filters** are the main extension mechanism. `JobFilterAttribute` subclasses implement any of the client/server/state filter interfaces. They are discovered via `GlobalJobFilters` and `JobFilterAttributeFilterProvider`, which reads attributes on the job's type and method.
5. **Job activation**: `JobActivator` / `JobActivatorScope`. `Masterly.NightShift.NetCore` supplies the DI-container-backed activator and `IHostedService` integration. Servers added with `AddNightShiftServer` put a server filter in front of their filter provider (`NetCore/Hosting/JobLoggingScope.cs`) that runs each job inside `ILogger.BeginScope` (JobId, JobName, RecurringJobId, RetryCount); `ConfigureNightShiftJobLogging(o => o.BeginScope = false)` turns it off. `Masterly.NightShift.AspNetCore` adds dashboard middleware and `IApplicationBuilder` extensions.

### Job chains

`Jobs/JobChain*.cs` and the partial `JobChains.*.cs`. A chain is recorded in the hash `chain:{id}` and listed in the set `chains`; `JobChainStepFilter`, the first default global filter, lets a step run only when the record lists its job. `docs/jobs/chains.md` describes the behavior; what a contributor must keep:

- **The lease.** A client that creates, retries or replaces a chain writes the `changing` entry into the record first (`JobChains.Lease.cs`, 2 minutes, renewed while it works, compared with the storage's clock where it has one), and the record that lists the jobs last, with the `ChainRecorded` marks of the steps in the same transaction. No step starts while the lease is live.
- **The first step of a chain that is being created is looked at again, not held.** For the first 5 seconds of a creation (`JobChainStepFilter.QuietTime`, by the lease's clock) the filter calls `TryLookAgain` with a pause of 10 to 250 ms (`WorkerWaits.MinPause`/`MaxPause`), so the worker keeps the job and the step's history shows nothing. When the pool's `WorkerWaits` doesn't offer it (budget used up, 5 seconds per job passed), after the 5 seconds, and for a retry or a replacement, the filter holds the step in the Scheduled state (`WaitingReasonFormat`).
- **A retry happens completely or not at all.** `RetryChainFrom` holds its step with `JobChains.RetryHold`, a Scheduled state of 2 minutes 15 seconds whose `ChainRetry` job parameter (`RetryMarker`: the record's generation, the step's state, data and expiry) is written in the same transaction (`JobChains.RetryHold.cs`). A worker that takes the step with that parameter, no live lease and the record still at that generation puts the step back with `ReplaceCandidateState(RestoredState)`, with an `AbandonedRetry` entry (the marker's id) in the state data, and deletes what the retry created (`DeleteAbandoned`, best effort); a step whose method can't be loaded is put back too. The note is checked by its id: the client's own put-back (`RestoredState.HeldFor`, checked under the job's lock by `EnsureHeldFor`) applies only while the step still carries that retry's marker, and the release after a recorded retry (`ChainCleanup.ReleaseRetry`) only while the step is held or was put back for it, so a later requeue, automatic retry or another retry is left alone. When the hold ends, the step goes to its queue as a job enqueued by hand does, so no schedule policy decides it: a step with a queue of its own gets there without a state change, so `SchedulePolicyFilter`, which checks a job a worker takes from the Scheduled state, leaves one alone while it carries `ChainRetry`. `ReplaceChain` and `DeleteChain` judge a step held by an abandoned retry by the state in its marker.
- **`RestoredState` is not a new event.** It applies a stored state again with its data. Handlers and the filters that keep data in step with the state go by its name; filters that react to an outcome must leave it out: no automatic retry, alert, monitor, statistics count or activity feed entry (`ActivityFeed` skips it). A new filter that reacts to Failed, Succeeded or Deleted must skip `JobChains.RestoredState` too.
- **Fan-in outcomes outlive the parents.** A parent that finishes writes what it finished as for each fan-in child (plain or a chain join) in its own state transaction, without a lock: one field, the parent's id, in the hash `fan-in:{childId}` (`FanInContinuationsSupportAttribute.GetOutcomesKey`), which the child's `FanInOutcomes` parameter names. The state change that takes the child out of Awaiting removes the hash; a parent that wrote for a child decided meanwhile removes its field after its commit. `RecordOutcomes` writes, under each parent's lock, for a child stored after its parents finished and for chain maintenance. A child is listed in `fan-in:unconfirmed` before it registers on its parents, scored half an hour ahead; chain maintenance then removes the hash of one that has no state (`ForgetIfNeverCreated`). While a parent's job exists its state decides; once it is gone, the written outcome. The filter counts a gone parent with nothing written as deleted; chain maintenance (`GetKnownParentState`) counts it as not finished and writes missing outcomes while the jobs exist. A waiting step that nothing can start any more (`JobChainInfo.StrandedSteps`) doesn't keep the record alive.
- **Step outcomes outlive the jobs.** A step of a recorded chain (its job has `ChainRecorded`) that finishes writes what it finished as into the hash `chain-outcomes:{id}` (`JobChains.GetStepOutcomesKey`, one field per job) in its own state transaction (`KeepOutcomeOfStep`, from `JobChainStepFilter.OnStateApplied`), also a step created in a final state (a join a retry skips at once), but not a step deleted as a refusal of a chain that no longer lists it. A step never sets its TTL (setting it touches every field, and the steps of a group finish side by side): every write that keeps the record longer does (`ExtendRecordCore`, `ChainRecord.Write` of a later generation, a look at a finished chain), always the record's time plus `RecordRefreshSlack`, and `DeleteChain` and unlisting remove the hash, also fields nobody gave a TTL. `RetryChainFrom(chainId, stepJobId)` retries a step whose job is gone (`Retry` reads the chain from the job only without it). `RetryChainFrom` reads it for the steps beside the retried one before anything changes (`ReadOutcomesBeside`; a gone step with nothing kept refuses the retry) and hands it to the new joins as `AwaitingJobsState.KnownOutcomes` (internal, never stored): `RegisterChild` counts a parent whose job is gone as that outcome and writes it into the child's `fan-in:{childId}`. `JobChainStepInfo.FinishedAs` exposes it; `Decide`, `BlockedLevels`, `FailedCount`, the flowchart and `Redrive` go by it, except that a single-parent step isn't decided by it with `UseResultsInContinuations`.
- **Records and retention.** The record is kept while the job of a step exists in a state other than Succeeded or Deleted, then for `JobChain.RecordRetention` (`UseChainRetention`, 30 days by default, a static property). `ChainRecorded` holds the writer's retention in seconds (`true` from earlier builds means this process's), so no server takes a record for expired sooner than its writer kept it.
- **Maintenance reads an index, never the list.** `JobChainMaintenanceProcess` (every 5 minutes, one server at a time, bounded per run) reads the sets `chains:cleanup` (changes left to finish), `chains:soon` (looks asked for by a step that left Failed, Succeeded or Deleted; entries `{chainId}|{id}`, removed only by the look they asked for), `chains:expiring` (when a finished chain leaves `chains`), `chains:lost` (a chain whose record the storage lost, kept listed while its steps run, until the longest retention in the hash `chains:retentions`, where each process writes its own once per storage, after its last look; 36,500 days when that hash can't be read) and `chains:due` (when a chain is looked at next); a chain has its place in one of the last three at a time. A look (`JobChains.Look`, under `lock:chain:{id}`) re-drives the waiting steps that were never told to start, extends the record, and writes the chain's next place while it still holds the lock. The hash `chains:index` tracks the backfill of chains listed by earlier builds (`again` has it gone through once more; each process re-reads it every `IndexCheckInterval`, an hour); `chains:joins`, which an earlier build may still write during a rolling upgrade, is emptied entry by entry, never at once, and a step of an earlier build's chain that changes state asks for its chain's place (`PlaceChainOfEarlierBuildAfterCommit`). These sets are shared by every chain: write them after the commit of a state change (`LookSoonAfterCommit`), never inside it.

### Storage abstraction

`JobStorage` is the entry point every storage implements. It exposes `IStorageConnection` (reads, fetch, distributed locks), `IWriteOnlyTransaction` (atomic writes), `IMonitoringApi` (dashboard queries), and optional extra server processes. Newer optional capabilities are advertised through `JobStorage.HasFeature(...)` / `JobStorageFeatures` and the `JobStorageConnection` / `JobStorageTransaction` base classes, rather than new interface members. `Connection.GetQueueEntryId` (`JobStorageConnection.GetQueueEntryId(IFetchedJob)`: stable for an entry across put-back and re-delivery, unique per entry) lets a job with several queue entries run once: the worker records it as `QueueEntry` in the Processing state, and `BackgroundJobStateChanger` refuses Processing for a job that is Processing under another entry (the worker then removes its own entry). A connection that throws `NotSupportedException` from `GetQueueEntryId` although the storage reports the feature makes the worker warn once and run jobs without the guard. Every storage of this repository implements it. **Adding a member to these interfaces breaks third-party storages** (Redis, Postgres, Mongo, and others live in other repos), so extend via features/base classes.

`Masterly.NightShift.SqlServer` is the reference implementation:

- `SqlServerStorage` / `SqlServerStorageOptions`: configuration and connection management, on `Microsoft.Data.SqlClient` (the package references it; `SqlClientFactory` can wrap its connections). `SqlServerStorage` takes a connection string, never a name: a text without `key=value` throws.
- `SqlServerConnection`, `SqlServerWriteOnlyTransaction` (batched via `SqlCommandBatch`/`SqlCommandSet`), `SqlServerMonitoringApi`, and the internal static `SqlServerDistributedLock` (`sp_getapplock` helpers).
- A write transaction is sent as one command (`TryCommitInOneRoundTrip`): `set transaction isolation level read committed` (a pooled session keeps the level its last user set, and repeatable read would deadlock parameter and state writes), `begin tran`, every command with its parameters renamed (`@key` becomes `@key_3`), `commit tran`. It falls back to SqlClient's transaction and a command batch for custom queues, more than 64 commands or 2000 parameters, or batching turned off. `begin tran` and `commit tran` must stay in the same command: SQL Server raises error 266 when a parameterized command leaves a transaction open, so a job's insert can't share a commit with its first state that way. Concurrent job creation goes through `WriteCoalescer` (`SqlServerStorage.JobInserts` and `Commits`): up to `MaxConcurrentWriters` callers write alone, the rest in groups, and only transactions without locks are grouped. A single job is inserted without a table variable, because tempdb contention under concurrent callers cost more than it saved. A job's parameters are inserted with `insert ... select @jobId, Name, Value from (values ...) as p (Name, Value)`, the job's id once for all rows, never `values (@jobId, ...), (@jobId, ...)`: with the id repeated in each row, a plan compiled while the `Job` table was empty or nearly so checked the foreign key with a scan of `Job`, which waited on the uncommitted rows of other creators, and concurrent creators deadlocked (error 1205) until the plan was compiled again (`ConcurrentJobCreationFacts`). With `DELAYED_DURABILITY` allowed for the database (`UseDelayedDurability`), the job insert, the fetch and a transaction that only moves jobs to Processing commit without waiting for the disk; every other commit waits, and so does a transaction that writes a job parameter (`CommitsWithoutWaitingForTheDisk`).
- Job parameters can be set inside a write transaction (`SqlServerWriteOnlyTransaction.SetJobParameter`, feature `Transaction.SetJobParameter`), so a chain's `ChainRecorded` marks commit with its record and `Lease`, `StaleRestarts`, the cleared `HeldQueue`, `DueAt` and `ScheduledFor` with their state change. Inside one transaction the parameter commands run before the job rows, after the application locks, ordered by job and name, on every commit path: outside a transaction `SqlServerConnection.SetJobParameter` locks the parameter's row and then reads the job's row, so the other order would deadlock with it. Keep that order. A parameter of a job that doesn't exist is skipped and the rest of the transaction commits, on every storage (the conformance suite holds them to it).
- Queues are pluggable via `IPersistentJobQueueProvider`. `SqlServerJobQueue` is the default. Fetching happens either through sliding invisibility timeouts (`SqlServerTimeoutJob`) or the legacy transactional mode (`SqlServerTransactionJob`). `SqlServerHeartbeatProcess` keeps the fetched jobs alive in batches (padded to 1, 10, 50, 100 or 500 rows, so plans are reused) with `readpast`: it opens its connection first, takes the lock of a batch's jobs without waiting (`TryBeginKeepAlive`, skipping a busy job until the next pass) only while that batch's statement runs (at most 5 seconds), and takes a job for fetched by another worker only from its committed, unlocked row. A commit that removes a job from its queue holds that job's lock, so no keep-alive changes `FetchedAt` meanwhile. Never let one job's keep-alive wait for another's, or for a pooled connection, while it holds a job's lock.
- Background maintenance: `ExpirationManager`, `CountersAggregator`, `SqlServerHeartbeatProcess`.
- **Schema migrations** live in the single script `Schema/Install.sql`, embedded as a resource. It steps through `@CURRENT_SCHEMA_VERSION` up to `@TARGET_SCHEMA_VERSION`, which is currently 9. A schema change means adding a new versioned block and bumping the target. `DefaultInstall.sql` is generated from it by the `DefaultInstall.tt` T4 template, so don't hand-edit it.

### Telemetry

`UseTelemetry()` (no package dependencies: it uses `System.Diagnostics`) registers `Diagnostics/TelemetryFilter`, a global client and server filter. It emits `create`/`process` spans from the `Masterly.NightShift` `ActivitySource` and the `nightshift.job.*` instruments from the `Masterly.NightShift` `Meter` (names in `NightShiftTelemetry`). The creating trace context travels in the `TraceParent`/`TraceState` job parameters. It must stay cheap when nobody listens: check `HasListeners()`/`Enabled` before doing work, and never read job parameters otherwise. Server filters that report how a run ended (telemetry, `JobInsightsAttribute`) classify it with the internal `Diagnostics/JobOutcome.cs` (`JobOutcomes.Classify`): canceled (filter cancel, abort, shutdown `OperationCanceledException`), retry-later (`RetryLaterException`), failed, succeeded. `tests/Masterly.NightShift.SqlServer.Tests/TelemetryFacts.cs` checks the whole path end to end.

### Rules for features built on the storage

These come from bugs found in review; follow them in new code:

- **Never write a cluster-wide hot key inside a state transaction.** Every state change would serialize on it (on SQL Server a list insert X-locks all rows of its key). The activity feed is opt-in (`UseActivityFeed()`) and written after the commit by `ActivityFeedWriter`; queue insights also write after the commit. Use `RunAfterCommit` for side effects that must wait for the commit, and make them best-effort.
- **Statistics and bookkeeping must never fail a job.** Catch and log storage errors in filters whose purpose is observation (`JobInsightsAttribute`, `QueueInsightsFilter`, `AuditLog`).
- **Check features before optional members.** Call `JobStorage.HasFeature(JobStorageFeatures.ExtendedApi)` (or the specific feature) before using `ExpireSet`, `GetRangeFromSet` and the other `JobStorageConnection`/`JobStorageTransaction` members a storage may not override; degrade gracefully when the feature is missing. A default global filter that skips this breaks every job on such storages.
- **Keep keys short.** SQL Server stores keys and hash fields in 100 characters, set values in 256, job parameter names in 40, state names in 20 and queue names in 50, and the SQL Server storage now throws `ArgumentException` past those limits. Keys built from user input or templates must be bounded: `ConcurrencyControl.ShortenResource`, `JobTags` and `DrainMode` keep a readable prefix and add a hash.
- **Decide on committed data.** Logic that reads other jobs' states to decide something (fan-in continuations) must run after the deciding transaction commits, under the target job's lock with an expected state, or concurrent finishers race.
- **No storage connection enlists in an ambient transaction.** Suppress the caller's `TransactionScope` (`TransactionScopeOption.Suppress`, only when `Transaction.Current` is set) around everything that may open a connection: `SqlServerStorage` around the connection factory and `Open`, and `EntityFrameworkCoreStorage.SuppressAmbientTransaction()` around every use of a storage context, because EF Core enlists or refuses on each use, not only on open. A connection handed in already open, or a context whose connection the application enlisted, is used as it is. The EF Core staging API (`NightShift()`) is the only way into the caller's transaction.
- **Judge heartbeats by the storage's clock.** A storage with `Connection.GetUtcDateTime` writes server heartbeats with its own clock, so code that tells a live server from a stopped one, or a late recurring job from one on time, compares with that clock: the internal `Dashboard/StorageClock.cs` for `/health` and `/metrics` (one clock read per request, also when the report is cached), `RazorPage.StorageUtcNow ?? ApplicationUtcNow` on pages, and the same read through the public API in the health check of `Masterly.NightShift.AspNetCore`, which can't see the class. A storage that reports the feature must write and time out heartbeats with the clock `GetUtcDateTime` answers with. Due-time decisions do the same: `SchedulePolicyFilter` and `RunWindowAttribute` judge a job by `Filters/Timing/StorageTime.cs`, and `TriggerJob` by the storage's clock, never moving a recurring job's `LastExecution` back, because the schedulers find jobs due by that clock.
- **A disposed storage connection lets go of its distributed locks,** those whose handles weren't disposed too, as SQL Server does when a session closes (`ReentrantLocks.ReleaseAll` in the storages of `src/Shared/Storage` and EF Core; on SQL Server a connection that may still hold a session lock isn't returned to the pool). Core's filters rely on it, and the conformance suite checks it.
- **Every write to the drain-mode hash `hangfire:control` takes `lock:hangfire:control`** (`DrainMode`, 15 seconds): a resume rewrites the hash without the field it ends (`RemoveHash`, then `SetRangeInHash`, one transaction), so a write outside the lock could be lost. A deployment check that can't take it is tried again within a second (`PauseLockTimeoutException`), like one that can't take the fencing lock.
- **Dashboard writes are POSTs with a server-side read-only check**, routed through `CommandDispatcher`/`BatchCommandDispatcher` or with the same checks; GET pages never write. Text from jobs reaches HTML only through Razor's encoding or jQuery's `.text()`. A value put into a URL's path segment goes through `RouteValues.Encode` (`Url.JobDetails`, `Url.Queue`; `NightShift.routeValue` in scripts), which escapes `%`, `/` and `~` as `~25`, `~2F`, `~7E` so no host's path decoding turns one id into another; scripts read ids and names from the markup with `.attr()`, never `.data()`, which turns JSON-looking text into something else.

### JSON serialization

All JSON goes through System.Text.Json; Newtonsoft.Json is not referenced. `Common/SerializationHelper` holds isolated internal options and the user options set by `UseSerializerSettings(JsonSerializerOptions)` / `UseRecommendedSerializerSettings(...)`. The options read leniently (case-insensitive names, quoted numbers, enum names or numbers, public fields), so data written by the previous Newtonsoft-based versions stays readable. User options are kept as a write/read pair: data is written exactly as the user's options say, and the read copy always adds the lenient settings. `Common/JsonConverters.cs` adds what System.Text.Json lacks: `IState` values are written with a leading `"$type"` (`StateJsonConverter`, used by `SerializationOption.TypedInternal`), `object` values become primitives (and keep `"$type"` under the internal/recommended options), arrays may be wrapped as `{"$type","$values"}`, plus `System.Type`, `CultureInfo` and `XElement`. These converters are appended to user options too, after the user's own, so the user's win; that includes converters added in the `UseRecommendedSerializerSettings(callback)`. A value whose declared type is an interface or abstract class that no converter handles is written with a leading `"$type"` under any options (`TypeNamedJson`, shared with the state and object converters) and read back through the type resolver. The resolver modifiers in `Common/JsonConverters.cs` (also applied to user options, reading only) read what Newtonsoft read: collections wrapped as `{"$type","$values"}` and dictionaries with a leading `"$type"` (read as the declared type, the name ignored), structs whose only public constructor sets their get-only properties, and get-only collection properties. Library data the user options can't write (`NotSupportedException`) is written with the internal options. Only a leading `"$type"` (after one `"$id"`, as Newtonsoft wrote with `PreserveReferencesHandling`) names a type, and a value whose own members include `"$type"` or `"$values"` is written wrapped (`{"$type": its type, "$values": {its members}}`), so stored data can never choose the type it is read back as; keep both rules in any converter that reads or writes type names. Dashboard input (`DeserializeInput`) refuses a `"$type"` in `object` values and resolves interface values only among loaded types, by name or by what the configured type serializer writes, loading nothing; job-function payloads (`DeserializeData`) keep a `"$type"` in `object` values as data. Types System.Text.Json would write as read-only members have compatibility converters (`BigInteger`, `Rune`, `Index`, `Range`, `TimeZoneInfo`, text `TypeConverter`s), and `InvocationData.SerializeJob` refuses a struct argument that wouldn't read back, except in a job read from storage (`Job.ArgumentsReadBack`), which runs with what was read. Dashboard JSON uses `Dashboard/DashboardJson.Create(...)` (camelCase, UTC dates).

### Data compatibility

`GlobalConfiguration.SetDataCompatibilityLevel(CompatibilityLevel.Version_110/170/180)` controls the serialized payload format, so servers on older versions can still process jobs. Any change to serialization (`InvocationData`, state data, `SerializationHelper`) must respect the configured level. Core tests use `[DataCompatibilityRangeFact]` / `[DataCompatibilityRangeTheory]` (`tests/Masterly.NightShift.Core.Tests/Utils/`) to run a test across a range of levels: each test case is repeated per level (display name suffix like `[Version_170]`) and sets `GlobalConfiguration.CompatibilityLevel` in `PreInvoke`/`PostInvoke`.

### Multi-targeting

Every library package targets `net8.0;net10.0` (.NET Framework, `netstandard2.0` and .NET 7 or earlier are not supported: the user decided this on 2026-11-08; don't reintroduce them). `Masterly.NightShift.EntityFrameworkCore` references EF Core per target framework, like NetCore's Microsoft.Extensions packages: 8.0.x on `net8.0` (EF Core 9 and later need .NET 9) and 10.0.x on `net10.0`. ## Conventions

- Code style is enforced by the build: `.editorconfig` sets the rules to warning, `EnforceCodeStyleInBuild` is on (root `Directory.Build.props`), and the libraries treat warnings as errors. Use C# 8 to 14 features: file-scoped namespaces, implicit and global usings (`<Using>` items in each `.csproj`), primary constructors, records for read-only data, collection expressions, pattern matching, `extension` blocks, the `field` keyword and raw string literals. Locals use explicit types, not `var`, with target-typed `new()` (`Foo foo = new();`); the build enforces it (IDE0008, IDE0090), and `var` stays only for anonymous types. Empty and initialized collections use collection expressions (`List<Job> jobs = [];`). Every `if`, `else`, loop, `using` and `lock` body has braces; the build enforces it (IDE0011). `max_line_length = 120` in `.editorconfig` is an editor guide: nothing enforces it. Parameters are annotated with `[NotNull]`/`[CanBeNull]` from `Masterly.NightShift.Annotations`. To apply the rules, run `dotnet format style` with only `net10.0` in `<TargetFrameworks>`: with two target frameworks it stacks the fixes of both into one file, then build both. Don't let it fold `Add` calls into a collection expression where a comment says why they are separate (`GlobalJobFilters`), and don't give a member declared as a read-only interface a `[]` where something adds to it. Don't use `required` on a type stored as JSON, and don't make a type a record if it changes after creation.
- Nullable reference types are on in every project (`<Nullable>enable</Nullable>`). Base an annotation on evidence: what the code passes, returns and checks; for storage interfaces, what `Masterly.NightShift.SqlServer` returns. Keep the JetBrains attributes, and fix what the compiler reports instead of suppressing it. A member always set before use stays non-nullable with `= null!`. Every `!` has a comment saying why the value can't be null. Exceptions: `Common/ExpressionUtil` and `CachedExpressionCompiler`, ported from ASP.NET MVC, are `#nullable disable`, and the test projects don't report the `nullable` warning group, because tests pass `null` on purpose. Job IDs returned by `Create`/`Enqueue`/`Schedule`/`ContinueJobWith` are deliberately `string?`, because creation can be canceled by filters. List what differs from Hangfire in `docs/changes-from-hangfire.md`. `LangVersion` is `latest`.
- Don't read `DateTime.UtcNow` in library code: use `JobClock.UtcNow`, so `UseTimeProvider` controls it. Dedicated lock objects are `NightShiftLock`, an alias of `System.Threading.Lock` on .NET 9 and later and of `object` on `net8.0`; don't use it with `Monitor`.
- Files inherited from the earlier project start with its LGPL license header, which must stay; new files need no header. SQL scripts use the same header as `--` comments.
- Tests use xUnit v3 (`xunit.v3.mtp-off`, i.e. the classic VSTest runner, so `dotnet test` and `--filter` work as usual) + Moq. Test classes are named `*Facts` and mirror the `src/` folder layout. Reusable context mocks are in `tests/Masterly.NightShift.Core.Tests/Mocks`. All test assemblies run with `[assembly: Parallelization(MaxThreads = 1)]`. Dashboard pages are tested by rendering them with `tests/Masterly.NightShift.Core.Tests/Dashboard/Pages/PageRenderer.cs`, which mocks the storage with empty answers. Custom `BeforeAfterTestAttribute`s must not use `Monitor` (v3 can call `After` on another thread); use `SemaphoreSlim`. SQL Server tests use `[CleanDatabase]` to truncate tables between tests, and tests that touch static/global state use `[GlobalLock]`/`[StaticLock]`.
- To release, raise `<Version>` in `src/Directory.Build.props` (the assembly versions are generated from it) and add a `## [x.y.z] - yyyy-mm-dd` section to `CHANGELOG.md` that opens with a one-line summary: `publish.yml` uses that section, minus its heading, as the GitHub Release body. The date is the release gate: while the heading reads `## [x.y.z]` without a date, `publish.yml` stops with a notice and publishes nothing, and it fails when the section is missing or empty. Don't date the heading casually; merging a dated heading to `master` is the release act.
- CI: `.github/workflows/build.yml` builds, tests (on `net8.0` and `net10.0`) and packs on Windows (LocalDB), then a `consumer` job installs the packed packages into new apps outside the repository and builds them with `-warnaserror`: `dotnet new web` on net8.0/net10.0 with `Masterly.NightShift`, a net8.0 console with Core + SqlServer that runs a job against LocalDB, and a net8.0 Worker Service with only NetCore + SqlServer built with the .NET 8 SDK (guards the source generator's Roslyn pin) that fails if a Microsoft.Extensions package resolves above 8.x, and runs the `net8.0` and `net10.0` tests on Linux (SQL Server and Redis service containers, and a one-member MongoDB replica set started by a step, since service containers can't take `--replSet`) for every push and PR. The Windows job runs every test project; the Redis and MongoDB tests skip there.
