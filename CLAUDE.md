# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Masterly.NightShift started from the source of an earlier open-source library (see `NOTICE.md`) and was renamed throughout. Existing data keeps working: the SQL Server schema is still named `HangFire`, the drain-mode storage key is still `hangfire:control`, and `TypeHelper` maps type names stored by the earlier library (`Hangfire.*, Hangfire.Core`) to the new types. Files that carry a license header naming the earlier project must keep it (`NOTICE.md`). Everything written for this project is MIT (`LICENSE.txt`). The packages declare `MIT AND LGPL-3.0-or-later` and carry `LICENSE-LGPL-3.0.txt` and `LICENSE-GPL-3.0.txt`.

Masterly.NightShift is a .NET library for fire-and-forget, delayed, recurring, and continuation background jobs, persisted to pluggable storage. This repo ships the NuGet packages `Masterly.NightShift.Core`, `Masterly.NightShift.SqlServer`, `Masterly.NightShift.NetCore`, `Masterly.NightShift.AspNetCore`, and the `Masterly.NightShift` meta-package (`src/Masterly.NightShift`). It is a library consumed by many old and new runtimes, so **binary/API compatibility across a wide range of target frameworks is a primary constraint**.

## Build and test

Everything builds and packs with the dotnet CLI; package metadata (authors, license, icon, readme, version) lives in `src/Directory.Build.props`, and each package's description in its `.csproj`. `Masterly.NightShift.Core` packs the source generator as an analyzer and `build/Masterly.NightShift.Core.props`. Cronos and Dapper are normal package dependencies (they are no longer merged into the assemblies).

```
dotnet build Masterly.NightShift.slnx -c Release
dotnet pack src/Masterly.NightShift.Core -c Release --no-build -o artifacts   # likewise SqlServer, NetCore, AspNetCore, and src/Masterly.NightShift (meta-package)
```

Run the build and the tests on `net8.0` and `net10.0`, and on Windows also on `net48`, before proposing a pull request.

Day-to-day with the dotnet CLI:

```
dotnet build Masterly.NightShift.slnx -c Release
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0 --filter "FullyQualifiedName~Masterly.NightShift.Core.Tests.Server.WorkerFacts"
dotnet test tests/Masterly.NightShift.Core.Tests -f net8.0 --filter "FullyQualifiedName~WorkerFacts.Execute_TakesConnectionAndReleasesIt"
```

- Test projects target `net48;net8.0;net10.0`. Use `-f` to pick one. `net48` runs the libraries' `netstandard2.0` build on .NET Framework: Windows only (it still compiles elsewhere, with reference assemblies from NuGet), compiled with C# 12 like `net8.0`, and AspNetCore.Tests uses the ASP.NET Core 2.x packages there. Tests that can't apply on .NET Framework (telemetry, `WebApplication` and endpoint routing, IANA time zone ids, static abstract interface members, keep-alive URL resolution) are excluded with `#if NET8_0_OR_GREATER`. `tests/Shared/` holds stand-ins for newer BCL APIs, compiled into every `net48` target. `tests/Masterly.NightShift.Core.Tests` and `tests/Masterly.NightShift.SqlServer.Tests` test their packages; `tests/Masterly.NightShift.AspNetCore.Tests` tests `Masterly.NightShift.NetCore` and `Masterly.NightShift.AspNetCore` together (DI registration, hosted services, endpoint mapping, keep-alive). Building requires the .NET 10 SDK (pinned in `global.json`).
- `TreatWarningsAsErrors` is on for all `src/` projects, and .NET analyzers run in `Recommended` mode (`src/Directory.Build.props`). Analyzer warnings break the build.
- Package versions are managed centrally in `Directory.Packages.props`; `PackageReference` items have no `Version`. Library dependencies are kept current (`dotnet list Masterly.NightShift.slnx package --outdated`); raising one raises the minimum consumers get. Exceptions: `Microsoft.CodeAnalysis.CSharp` stays at the oldest Roslyn the generators need (see the comment there); the Microsoft.Extensions packages of `Masterly.NightShift.NetCore` (and HealthChecks in `Masterly.NightShift.AspNetCore` on `netstandard2.0`) stay at the oldest serviced version for each target framework (8.0.x on `netstandard2.0` and `net8.0`, 10.0.x on `net10.0`), so apps keep their runtime's stack; and the source-only packages (LibLog, StackTraceParser/Formatter, MoreLinq) are references with `ExcludeAssets="contentFiles"`: the code compiled is the vendored copy, so bumping them changes nothing. System.Text.Json is referenced on `netstandard2.0` only.
- NuGet lock files (`packages.lock.json`) are used. After changing a package, run `dotnet restore Masterly.NightShift.slnx --force-evaluate`. CI restores in locked mode.
- **The public API has no baseline yet.** Nothing has been published under the `Masterly.NightShift.*` IDs. `dotnet pack` runs package validation, which checks that the API agrees across target frameworks. After the first release is on nuget.org, set `PackageValidationBaselineVersion` in `src/Directory.Build.props` to it, so later breaks are caught, and record intentional ones in `docs/breaking-changes.md`.

### Test prerequisites

- **SQL Server tests** need a reachable SQL Server. Set `NightShift_SqlServer_ConnectionStringTemplate` to a connection string with a `{0}` database placeholder, for example `Server=.\sqlexpress;Database={0};Integrated Security=True;TrustServerCertificate=True;` or, with LocalDB, `Server=(localdb)\MSSQLLocalDB;Database={0};Integrated Security=True;TrustServerCertificate=True;`. The default is `Server=.\;Database={0};Trusted_Connection=True;...`. Each TFM uses its own database (`Masterly.NightShift.SqlServer.Tests.net8_0`, and so on), created on demand with a case-sensitive collation. To override the name, set `NightShift_SqlServer_DatabaseName`.
- Test projects use `extern alias ReferencedCronos` (see the `ChangeAliasesOfStrongNameAssemblies` target) so tests can reference Cronos without clashing with the copy the library uses.

## Architecture

### Source layout

Files are grouped by feature, and **namespaces don't follow folders**: most public types stay in `Masterly.NightShift` (or `Masterly.NightShift.Client`, `.Server`, `.States`, `.Storage`, `.Dashboard`...) wherever the file lives, so moving a file never breaks the API. Put a new file in the folder of its feature, keep the namespace the API needs, and put its tests in the same folder of the test project.

- `Masterly.NightShift.Core`: `Jobs/` (creating jobs, continuations, fan-in, batches, tags, notes, catalog), `RecurringJobs/`, `Scheduling/` (CRON helpers, `TimeText`), `Hosting/` (`BackgroundJobServer`, options, drain mode, activator, cancellation), `Filters/` (`Retries/`, `Concurrency/`, `Timing/`, `Behavior/`, plus the global collections), `Monitoring/` (alerts, audit log, activity feed, insights), `Configuration/` (`GlobalConfiguration` and its extensions). The infrastructure folders `Client/`, `Server/`, `States/`, `Storage/`, `Processing/`, `Dashboard/`, `Diagnostics/`, `Common/`, `Profiling/` and `Obsolete/` match their namespaces. `Logging/` holds `LateBoundLogProvider`, which makes every logger follow the provider set later with `UseLogProvider` (installed by a module initializer on net8.0+). Vendored code is in `App_Packages/`.
- `Masterly.NightShift.SqlServer`: the storage, connection, transaction and monitoring classes at the root; `Queues/`, `Locking/`, `Maintenance/`, `Schema/` and `Infrastructure/`.
- `Masterly.NightShift.NetCore`: `DependencyInjection/`, `Hosting/` and `AspNetCore/`.
- `Masterly.NightShift.AspNetCore`: dashboard middleware and endpoint mapping at the root, `Dashboard/` (ASP.NET Core adapters) and `HealthChecks/` (`AddNightShift` for `IHealthChecksBuilder`).
- Embedded resources are named after their path, so the dashboard's `Content/` stays where it is, and `Schema/Install.sql` keeps its old name through `LogicalName`.

User documentation is in `docs/` (start at `docs/README.md`); design notes are in `docs/architecture/`.

### Job lifecycle (Masterly.NightShift.Core)

1. **Client side** (`Client/`, `BackgroundJobClient`, `BackgroundJob` static facade, `RecurringJobManager`): a lambda expression is turned into a `Common.Job` (type + method + args). `Storage.InvocationData` serializes it. `IBackgroundJobFactory` → `CoreBackgroundJobFactory` creates it in storage, running client filters (`IClientFilter`) around creation.
2. **State machine** (`States/`): every transition goes through `IBackgroundJobStateChanger` → `StateMachine`/`CoreStateMachine`. Election filters (`IElectStateFilter`) can redirect the candidate state, which is how `AutomaticRetryAttribute` turns `Failed` into `Scheduled`. Apply filters (`IApplyStateFilter`) and `IStateHandler`s (`GlobalStateHandlers`) then perform the storage side effects inside one `IWriteOnlyTransaction`. Built-in states: Enqueued, Scheduled, Processing, Succeeded, Failed, Deleted, Awaiting (continuations). Work that must wait until the transaction is committed, such as raising an alert, goes through the internal `ApplyStateContext.RunAfterCommit` / `ElectStateContext.RunAfterCommit`: `BackgroundJobStateChanger` runs it after `Commit()` and drops it when the commit fails, so a retried state change doesn't do it twice. Work about something a filter already committed on its own (the circuit breaker's `CircuitOpened` alert) uses `ElectStateContext.RunAfterCommitAttempt`, which runs after the job's lock is released whether the commit worked or not. `CoreStateMachine` expires the job when `ApplyStateContext.JobExpires` (the new state is final, or a filter set the internal `ExpireInNonFinalState`, as failed-job retention does) and persists it otherwise; code that ties data to the job's lifetime (`JobConsoleStateFilter`) checks `JobExpires`, not `IsFinal`.
3. **Server side** (`Server/`, `Processing/`): `BackgroundJobServer` builds the list of processes: `Worker` (pool of `WorkerCount` threads), `DelayedJobScheduler`, `RecurringJobScheduler`, `ServerHeartbeatProcess`, `ServerWatchdog`, plus any storage-provided processes. It hands them to `BackgroundProcessingServer`, which runs them through `Processing/BackgroundDispatcher` + `BackgroundExecution` (retry/backoff loop). `Worker` fetches a job, moves it to Processing, calls `IBackgroundJobPerformer` (server filters `IServerFilter` wrap `CoreBackgroundJobPerformer`), then moves it to Succeeded/Failed.
4. **Filters** are the main extension mechanism. `JobFilterAttribute` subclasses implement any of the client/server/state filter interfaces. They are discovered via `GlobalJobFilters` and `JobFilterAttributeFilterProvider`, which reads attributes on the job's type and method.
5. **Job activation**: `JobActivator` / `JobActivatorScope`. `Masterly.NightShift.NetCore` supplies the DI-container-backed activator and `IHostedService` integration. Servers added with `AddNightShiftServer` put a server filter in front of their filter provider (`NetCore/Hosting/JobLoggingScope.cs`) that runs each job inside `ILogger.BeginScope` (JobId, JobName, RecurringJobId, RetryCount); `ConfigureNightShiftJobLogging(o => o.BeginScope = false)` turns it off. `Masterly.NightShift.AspNetCore` adds dashboard middleware and `IApplicationBuilder` extensions.

### Storage abstraction

`JobStorage` is the entry point every storage implements. It exposes `IStorageConnection` (reads, fetch, distributed locks), `IWriteOnlyTransaction` (atomic writes), `IMonitoringApi` (dashboard queries), and optional extra server processes. Newer optional capabilities are advertised through `JobStorage.HasFeature(...)` / `JobStorageFeatures` and the `JobStorageConnection` / `JobStorageTransaction` base classes, rather than new interface members. **Adding a member to these interfaces breaks third-party storages** (Redis, Postgres, Mongo, and others live in other repos), so extend via features/base classes.

`Masterly.NightShift.SqlServer` is the reference implementation:

- `SqlServerStorage` / `SqlServerStorageOptions`: configuration and connection management (supports both `System.Data.SqlClient` and `Microsoft.Data.SqlClient`).
- `SqlServerConnection`, `SqlServerWriteOnlyTransaction` (batched via `SqlCommandBatch`/`SqlCommandSet`), `SqlServerMonitoringApi`, `SqlServerDistributedLock`.
- Queues are pluggable via `IPersistentJobQueueProvider`. `SqlServerJobQueue` is the default. Fetching happens either through sliding invisibility timeouts (`SqlServerTimeoutJob`) or the legacy transactional mode (`SqlServerTransactionJob`).
- Background maintenance: `ExpirationManager`, `CountersAggregator`, `SqlServerHeartbeatProcess`.
- **Schema migrations** live in the single script `Schema/Install.sql`, embedded as a resource. It steps through `@CURRENT_SCHEMA_VERSION` up to `@TARGET_SCHEMA_VERSION`, which is currently 9. A schema change means adding a new versioned block and bumping the target. `DefaultInstall.sql` is generated from it by the `DefaultInstall.tt` T4 template, so don't hand-edit it.

### Telemetry

`UseTelemetry()` (net8.0+ only, so no new package dependencies) registers `Diagnostics/TelemetryFilter`, a global client and server filter. It emits `create`/`process` spans from the `Masterly.NightShift` `ActivitySource` and the `nightshift.job.*` instruments from the `Masterly.NightShift` `Meter` (names in `NightShiftTelemetry`). The creating trace context travels in the `TraceParent`/`TraceState` job parameters. It must stay cheap when nobody listens: check `HasListeners()`/`Enabled` before doing work, and never read job parameters otherwise. Server filters that report how a run ended (telemetry, `JobInsightsAttribute`) classify it with the internal `Diagnostics/JobOutcome.cs` (`JobOutcomes.Classify`): canceled (filter cancel, abort, shutdown `OperationCanceledException`), retry-later (`RetryLaterException`), failed, succeeded. `tests/Masterly.NightShift.SqlServer.Tests/TelemetryFacts.cs` checks the whole path end to end.

### Rules for features built on the storage

These come from bugs found in review; follow them in new code:

- **Never write a cluster-wide hot key inside a state transaction.** Every state change would serialize on it (on SQL Server a list insert X-locks all rows of its key). The activity feed is opt-in (`UseActivityFeed()`) and written after the commit by `ActivityFeedWriter`; queue insights also write after the commit. Use `RunAfterCommit` for side effects that must wait for the commit, and make them best-effort.
- **Statistics and bookkeeping must never fail a job.** Catch and log storage errors in filters whose purpose is observation (`JobInsightsAttribute`, `QueueInsightsFilter`, `AuditLog`).
- **Check features before optional members.** Call `JobStorage.HasFeature(JobStorageFeatures.ExtendedApi)` (or the specific feature) before using `ExpireSet`, `GetRangeFromSet` and the other `JobStorageConnection`/`JobStorageTransaction` members a storage may not override; degrade gracefully when the feature is missing. A default global filter that skips this breaks every job on such storages.
- **Keep keys short.** SQL Server stores keys and hash fields in 100 characters, set values in 256, job parameter names in 40, state names in 20 and queue names in 50, and the SQL Server storage now throws `ArgumentException` past those limits. Keys built from user input or templates must be bounded: `ConcurrencyControl.ShortenResource`, `JobTags` and `DrainMode` keep a readable prefix and add a hash.
- **Decide on committed data.** Logic that reads other jobs' states to decide something (fan-in continuations) must run after the deciding transaction commits, under the target job's lock with an expected state, or concurrent finishers race.
- **Dashboard writes are POSTs with a server-side read-only check**, routed through `CommandDispatcher`/`BatchCommandDispatcher` or with the same checks; GET pages never write. Text from jobs reaches HTML only through Razor's encoding or jQuery's `.text()`.

### JSON serialization

All JSON goes through System.Text.Json; Newtonsoft.Json is not referenced. `Common/SerializationHelper` holds isolated internal options and the user options set by `UseSerializerSettings(JsonSerializerOptions)` / `UseRecommendedSerializerSettings(...)`. The options read leniently (case-insensitive names, quoted numbers, enum names or numbers, public fields), so data written by the previous Newtonsoft-based versions stays readable. User options are kept as a write/read pair: data is written exactly as the user's options say, and the read copy always adds the lenient settings. `Common/JsonConverters.cs` adds what System.Text.Json lacks: `IState` values are written with a leading `"$type"` (`StateJsonConverter`, used by `SerializationOption.TypedInternal`), `object` values become primitives (and keep `"$type"` under the internal/recommended options), arrays may be wrapped as `{"$type","$values"}`, plus `System.Type`, `CultureInfo` and `XElement`. These converters are appended to user options too, after the user's own, so the user's win; that includes converters added in the `UseRecommendedSerializerSettings(callback)`. A value whose declared type is an interface or abstract class that no converter handles is written with a leading `"$type"` under any options (`TypeNamedJson`, shared with the state and object converters) and read back through the type resolver. The resolver modifiers in `Common/JsonConverters.cs` (also applied to user options, reading only) read what Newtonsoft read: collections wrapped as `{"$type","$values"}` and dictionaries with a leading `"$type"` (read as the declared type, the name ignored), structs whose only public constructor sets their get-only properties, and get-only collection properties. Library data the user options can't write (`NotSupportedException`) is written with the internal options. Dashboard JSON uses `Dashboard/DashboardJson.Create(...)` (camelCase, UTC dates).

### Data compatibility

`GlobalConfiguration.SetDataCompatibilityLevel(CompatibilityLevel.Version_110/170/180)` controls the serialized payload format, so servers on older versions can still process jobs. Any change to serialization (`InvocationData`, state data, `SerializationHelper`) must respect the configured level. Core tests use `[DataCompatibilityRangeFact]` / `[DataCompatibilityRangeTheory]` (`tests/Masterly.NightShift.Core.Tests/Utils/`) to run a test across a range of levels: each test case is repeated per level (display name suffix like `[Version_170]`) and sets `GlobalConfiguration.CompatibilityLevel` in `PreInvoke`/`PostInvoke`.

### Dashboard

`Dashboard/` is a self-contained, host-agnostic UI: `RouteCollection`/`DashboardRoutes` map paths to `IDashboardDispatcher`s (Razor pages, JSON stats, commands, embedded static resources). The ASP.NET Core adapter (`Masterly.NightShift.AspNetCore`) sits on top. OWIN support was removed.

- Pages are `.cshtml` files compiled to C# during every build by the `Masterly.NightShift.Dashboard.Generator` source generator (`src/Masterly.NightShift.Dashboard.Generator`, built on `Microsoft.AspNetCore.Razor.Language`, never shipped). Hand-written partial logic goes in the sibling `.cs` files. Nothing generated is checked in; to see the output, build with `-p:EmitCompilerGeneratedFiles=true` and look in `obj/<config>/<tfm>/generated`. The generator reproduces RazorGenerator's output byte for byte: Windows line endings on every OS, the `@* Generator: ... *@` options (visibility, `TrimLeadingUnderscores`), and lines holding only a Razor comment keep their whitespace.
- UI strings live in `Dashboard/Content/resx/Strings*.resx`, one file per locale. `Strings.Designer.cs` is generated.
- Static assets in `Dashboard/Content` must be listed as `EmbeddedResource` in `Masterly.NightShift.Core.csproj`.
- Dates are formatted by `Content/js/nightshift-intl.js` (browser `Intl` APIs). It's also Chart.js 2.x's date adapter, so moment.js isn't used. Its date arithmetic matches moment's exactly, including across daylight saving changes. Keep it that way: dashboard extensions and the realtime and history graphs rely on it. How the pages were moved off RazorGenerator is recorded in `docs/architecture/dashboard-razor-plan.md`.

### Multi-targeting

Every library package targets `netstandard2.0;net8.0;net10.0`. `netstandard2.0` is what .NET Framework (4.6.2+) consumers get. Code that needs newer BCL APIs is gated with `#if NET8_0_OR_GREATER`, and anything shared must still compile for `netstandard2.0`, so check before using a newer API. Small polyfills live in `Common/LanguagePolyfills.cs`. The job invoker generator's output must compile as C# 7.3, the default language version of .NET Framework and netstandard2.0 projects (no `#nullable` directive, no newer syntax); `samples/CSharp73Check` builds job code as C# 7.3 so the solution build catches a regression. `App_Packages/` holds vendored source-only packages (LibLog, StackTraceParser/Formatter), so don't modify them beyond their namespaces, which follow the rename.

## Conventions

- Match the existing code style, not modern C# defaults: block-scoped namespaces, `var` is used freely, and parameters are annotated with `[NotNull]`/`[CanBeNull]` from `Masterly.NightShift.Annotations`. Nullable reference types are being enabled file by file with `#nullable enable` (done: the client API (`BackgroundJob*`, `IBackgroundJobClient`, `RecurringJob*`, `IRecurringJobManager`), `BackgroundJobServer*`, the client/server/state filter interfaces and contexts, `IState` with the built-in states, and the storage contract (`JobStorage`, `IStorageConnection`, `JobStorageConnection`, `IWriteOnlyTransaction`, `JobStorageTransaction`, `IFetchedJob`, `JobData`, `StateData`), and the monitoring API with its DTOs). The most-used entry points are annotated too: AddNightShift/AddNightShiftServer, the ASP.NET Core dashboard and server extensions, UseSqlServerStorage with SqlServerStorageOptions, Cron, AutomaticRetryAttribute and JobActivator/JobActivatorScope/JobActivatorContext. Other public types aren't annotated yet (for example GlobalConfigurationExtensions, GlobalConfiguration, Job, the filter attributes other than AutomaticRetryAttribute, DashboardOptions, SqlServerStorage and the dashboard extension API), nor is internal code. For storage interfaces, base each annotation on evidence: what Masterly.NightShift passes, and what `Masterly.NightShift.SqlServer` returns. When converting a file, keep the JetBrains attributes, turn `[CanBeNull]` into `?`, and fix what the compiler reports instead of suppressing it. The compiler can't check interfaces, or values that come from files not converted yet, so review those by hand. Job IDs returned by `Create`/`Enqueue`/`Schedule`/`ContinueJobWith` are deliberately `string?`, because creation can be canceled by filters. List consumer-visible changes in `docs/breaking-changes.md`. `LangVersion` is `Latest`, but code must still compile for `netstandard2.0`, which .NET Framework 4.6.2+ consumers use.
- Files inherited from the earlier project start with its LGPL license header, which must stay; new files need no header. SQL scripts use the same header as `--` comments.
- Tests use xUnit v3 (`xunit.v3.mtp-off`, i.e. the classic VSTest runner, so `dotnet test` and `--filter` work as usual) + Moq. Test classes are named `*Facts` and mirror the `src/` folder layout. Reusable context mocks are in `tests/Masterly.NightShift.Core.Tests/Mocks`. All test assemblies run with `[assembly: Parallelization(MaxThreads = 1)]`. Dashboard pages are tested by rendering them with `tests/Masterly.NightShift.Core.Tests/Dashboard/Pages/PageRenderer.cs`, which mocks the storage with empty answers. Custom `BeforeAfterTestAttribute`s must not use `Monitor` (v3 can call `After` on another thread); use `SemaphoreSlim`. SQL Server tests use `[CleanDatabase]` to truncate tables between tests, and tests that touch static/global state use `[GlobalLock]`/`[StaticLock]`.
- To release, raise `<Version>` in `src/Directory.Build.props` (the assembly versions are generated from it) and add the notes to `CHANGELOG.md`.
- CI: `.github/workflows/build.yml` builds, tests (on `net48`, `net8.0` and `net10.0`) and packs on Windows (LocalDB), then a `consumer` job installs the packed packages into new apps outside the repository and builds them with `-warnaserror`: `dotnet new web` on net8.0/net10.0 with `Masterly.NightShift`, an ASP.NET Core 2.3 app on net48 (dashboard and health checks), a net48 console with Core + SqlServer that runs a job against LocalDB, and a net8.0 Worker Service with only NetCore + SqlServer built with the .NET 8 SDK (guards the source generator's Roslyn pin) that fails if a Microsoft.Extensions package resolves above 8.x, and runs the `net8.0` and `net10.0` tests on Linux (SQL Server container) for every push and PR. `publish.yml` pushes the packages to nuget.org after a successful Build on `main` (needs the `NUGET_API_KEY` secret; versions already published are skipped). `codeql-analysis.yml` runs CodeQL.
- Indentation is 4 spaces (`.editorconfig`).
