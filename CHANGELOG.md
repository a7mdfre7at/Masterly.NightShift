# Changelog

All notable changes to the Masterly.NightShift packages. Each version's section, without its heading, becomes the body of that version's GitHub Release, so it opens with a one-line summary.

## [1.0.0]

First release of Masterly.NightShift: reliable background jobs for .NET, built on Hangfire 1.8 and extended with new job types, filters, a redesigned dashboard and observability. Existing Hangfire SQL Server data keeps working.

- Initial release of Masterly.NightShift.
- Packages: `Masterly.NightShift`, `Masterly.NightShift.Core`, `Masterly.NightShift.SqlServer`, `Masterly.NightShift.NetCore`, `Masterly.NightShift.AspNetCore`.
- Targets `net8.0` and `net10.0`: .NET 8 and later only. .NET Framework, .NET 7 and earlier, and `netstandard2.0` consumers aren't supported.
- Licensed `MIT AND LGPL-3.0-or-later`: code written for Masterly.NightShift is MIT, code derived from Hangfire stays LGPL. The packages carry both license texts.
- JSON through System.Text.Json; no Newtonsoft.Json dependency. `UseSerializerSettings` and `UseRecommendedSerializerSettings` take `JsonSerializerOptions`. Data written by Newtonsoft-based versions, including `$type` states and arguments, stays readable.
- Reflection-free job invocation, interceptors, concurrency control, batches, fan-in continuations, run windows, a redesigned dashboard with live monitoring and insights, drain mode, Prometheus metrics, alerts, an audit log and OpenTelemetry-compatible telemetry. See What's new in the documentation.
- ASP.NET Core health checks (`AddHealthChecks().AddNightShift()`), `MapNightShiftHealth`/`MapNightShiftMetrics`, server options from configuration (`AddNightShiftServer(IConfiguration)`), Discord alerts, a testing guide and a web sample.
- `Masterly.NightShift.SqlServer` uses `Microsoft.Data.SqlClient` and references it, with a patched `System.Security.Cryptography.Pkcs`; `System.Data.SqlClient` is no longer supported, and apps don't add a driver themselves. A connection string name passed to `UseSqlServerStorage` throws at start-up.
- Every member Hangfire marked obsolete is removed (old `ContinueWith`, recurring job overloads without an ID, `BackgroundJobServer.Stop()`, `JobStorage.GetComponents()`, the no-op SQL Server transaction options and others). See `docs/changes-from-hangfire.md` for each replacement.
- The code uses .NET 8 APIs throughout (`ArgumentNullException.ThrowIfNull`, span overloads, `SHA256.HashData`), and the code that only served .NET Framework hosts (classic ASP.NET shutdown detection, thread abort handling) is gone.
- The dashboard has the NightShift look of the documentation site: the Orbit Moon logo, a deep-teal sidebar, mint accents in dark mode, teal-tinted surfaces and the same job-state colors (processing ember, succeeded green, failed rose, scheduled blue) in labels, graphs, the lineage diagram and the time-in-state bar. It serves the site's fonts, IBM Plex Sans and JetBrains Mono, itself (SIL Open Font License, see `THIRD-PARTY-NOTICES.md`), so it makes no external request. A custom state registered with `AddStateCssSuffix` gets the colors of its suffix.
- The code uses C# 8 to 14 and the build enforces the style: nullable reference types across the API, records, primary constructors, `extension` blocks, source-generated regular expressions and frozen lookup tables.
- `UseTimeProvider` sets the clock behind the timestamps the library writes. `BackgroundJobServer` supports `await using`. `AddNightShift` and `AddNightShiftServer` work on `IHostApplicationBuilder`.
- A job run and a state change no longer build and sort the job's filter list each time: `JobFilterProviderCollection` keeps it per job method until a filter collection changes, so `GetFilters` returns a shared list that must not be modified. Running a job through its filters takes about half the time and 60% less memory than in Hangfire 1.8.25.
- `EnqueueMany` creates many jobs in a few storage round trips, with client filters running for every job: one job per item (`jobs.EnqueueMany<EmailService, int>(userIds, (x, id) => x.SendWelcome(id))`), per method call or per `Job`. Storages can override the new `JobStorageConnection.CreateExpiredJobs`; SQL Server inserts the jobs of a group in one command.
- The SQL Server storage sends a transaction as one command, so a commit is one round trip instead of three, and creating a job takes two round trips instead of four. `UseTransactionalAcknowledge` is on by default. Callers that create jobs at the same time are written in groups beyond `MaxConcurrentWriters` (8). The new `AllowDelayedDurability` lets the commits that are safe to lose (fetching a job, moving it to Processing) skip the wait for the disk.
- The activity feed is opt-in (`UseActivityFeed()`) and written after commit, so it no longer slows down state changes.
- Fixes behaviour inherited from Hangfire 1.8.25, such as running the exact overload of a job method, clearer failure reasons when a job can't be loaded, SQL Server options that schema auto-detection no longer overrides, clear errors instead of silent truncation for over-long values, batched purges, dashboard CSRF protection when antiforgery isn't registered, and loggers that follow a provider set later. See `docs/changes-from-hangfire.md`.
- Start and end dates for recurring jobs (`RecurringJobOptions.StartAt`/`EndAt`), an opt-in retention period for failed jobs (`[ExpireAfter(..., IncludeFailed = true)]`, `UseFailedJobRetention`), a logging scope with the job id and name around every job (`AddNightShiftServer`), `CircuitBreakerAttribute.ExceptOn`/`OnlyOn`, a `retry_later` telemetry outcome, and a Microsoft Teams webhook format.
- `Masterly.NightShift.NetCore` needs Microsoft.Extensions 8.0.x on `net8.0` (10.0.x only on `net10.0`), so .NET 8 apps keep their runtime's stack.
- Job classes (`IJob`, `IJobHandler<TArgs>`, `client.Enqueue<TJob>()`, `client.Enqueue(args)`, `client.Enqueue<THandler, TArgs>(args)`, `AddNightShiftJobHandler`), `PerformContext.RetryCount`, recurring jobs declared in code and applied at start-up (`AddNightShiftRecurringJobs`, `RecurringJobSet`, with IDs from the class name and `%Section:Key%` schedules from configuration), `Cron.Every(TimeSpan)` for intervals CRON can keep exactly, and `BasicAuthDashboardAuthorizationFilter` for the dashboard.
- Job execution control, after TickerQ: `TerminateJobException` ends a job without retries as skipped, canceled or failed; `[SkipIfLate]` skips a run that starts too late; `[JobTimeout(OnTimeout = ...)]` fails or cancels a job that ran out of time without retrying it; `PerformContext.ScheduledFor`, `StartedAt`, `Lateness` and `RecurringJobId`; `IJobExceptionHandler` with `UseJobExceptionHandler` and `AddNightShiftJobExceptionHandler<T>()`; `storage.WaitForCompletionAsync` and `JobStateInfo.IsCompleted`. Telemetry reports a skipped run with the outcome `skipped`.
- Scheduling, after TickerQ: `RecurringJobOptions.SkipAfter` skips a run that starts too late (`LateStartFilter`, a new default global filter); `MisfireHandlingMode.RunLatest` runs only the latest missed occurrence within `SkipAfter`; `UseDefaultRecurringJobTimeZone`; each recurring job keeps its last 50 runs (`storage.GetRecurringJobRuns`), and `storage.GetNextOccurrences` lists its coming runs; `RecurringJobSet.RetireUndeclared` pauses jobs no longer declared instead of deleting them, `RecurringJobSet.Once` creates start-up work once per key, and `RecurringJobDto` has `SkipAfter`, `Declared` and `Retired`. The manifest carries `skipAfterSeconds`.
- Schedule policies, after TickerQ: business calendars (`SchedulePolicy`: allowed weekdays and daily windows, excluded dates and annual dates, `IScheduleDateProvider` dates, `Require`/`ExceptWhen` other policies, a time zone) stored by name with a revision (`SaveSchedulePolicy`, `UpdateSchedulePolicy`, `DeleteSchedulePolicy`, `EvaluateSchedulePolicy`, `FindNextAllowed`, `PreviewSchedulePolicy`). `Enqueue` and `Schedule` take `ScheduleOptions` (`Policy`, `WhenBlocked` = `MoveForward`/`Skip`/`Reject`, `SkipAfter`, `Queue`), applied by the new default global filter `SchedulePolicyFilter`; `RecurringJobOptions.Policy` leaves out blocked occurrences, and changing a policy reschedules its recurring jobs. `RecurringJobSet.AddPolicy` declares policies saved at start-up, `UseScheduleDateProvider` and `AddNightShiftScheduleDateProvider<T>` register date providers, and the manifest carries `policy`.
- Continuations and chains, after TickerQ: `JobContinuationOptions.OnlyOnFailedState` (when the parent fails for good) and `OnlyOnProcessingState` (when it starts), with the other continuations left waiting; `FanInMode.AnyFailed`, `AnyFailedOrCanceled` and `AllCompleted` and `ContinueJobWithJoin`; `PerformContext.ParentId` and `ParentIds`. `JobChain` builds workflows of steps, parallel branches and success or failure joins, created together and recorded (`GetChain`, `RetryChainFrom`, `ReplaceChain`, `DeleteChain` with `Cascade` or `Restrict`), and `RecurringJob.AddOrUpdateChain` creates one at each occurrence.
- Job functions, after TickerQ: `[JobFunction("name")]` methods and delegates registered with `AddNightShiftFunction` are created by name with a payload checked at creation (`EnqueueFunction`, `ScheduleFunction`, `RecurringJob.AddOrUpdateFunction`); `storage.DeletePendingJobs<T>()`, `DeletePendingFunctionJobs` and `DeletePendingJobs(filter)` cancel pending work.
- Reliability, after TickerQ: `UseStaleRestartLimit` fails a job picked up again too many times after its server stopped, and lease fencing (`StaleJobFilter`, a new default global filter) refuses a former owner's late state change; `UseDeploymentFencing` pauses servers of an older deployment; `BackgroundJobServerOptions.StartMode = Manual` and `IBackgroundJobServerControl` start and stop hosted servers from code; `[LongRunning]` and `LongRunningWorkerCount` give long jobs their own workers; `UseJobRetention` sets retention per state; `UseArgumentCompression` stores long arguments compressed.
- Observability, after TickerQ: `AddNightShiftJobLogs` writes a job's `ILogger` lines into its console; telemetry adds `nightshift.job.completed`, `retried`, `stale_restarts` and the `nightshift.job.lateness` histogram; job monitors (`DailyDeadlineMonitor`, `LongRunningMonitor`, `RepeatedFailuresMonitor`, `UseJobMonitor`) raise `MonitorIncident` and `MonitorRecovered` alerts; `AlertRule` filters any sink by kind, method and cooldown; webhooks get `Template`, retries (`RetryDelays`), a delivery history and `Alert.Id`.
- Dashboard, after TickerQ: a details page per recurring job with its next runs, its last 20 runs and a **From code** badge for jobs declared in code; a Chains page that draws each chain as a flowchart (parallel groups, outcomes, a card per step with its start condition, progress and timing), with zoom, full screen, the merged logs of its steps and **Retry from here**; a Policies page to edit schedule policies with optimistic revisions and preview a schedule against them; an About page with the configuration, global filters, job functions and monitors in effect. A chain step's job page links to its chain.
- Storages, after TickerQ: `Masterly.NightShift.EntityFrameworkCore` (any EF Core relational provider; `context.NightShift()` stages jobs so they commit or roll back with `SaveChanges`), `Masterly.NightShift.Redis` (StackExchange.Redis, one Lua script per transaction), `Masterly.NightShift.MongoDB` (replica sets, TTL indexes) and `Masterly.NightShift.InMemory` (development and tests). A shared conformance suite runs against all of them and against SQL Server.
- Review fixes: chains map the options of a `Then` or branch after a group to joins (`OnAnyFinishedState` also runs when a branch failed; `OnlyOnProcessingState` throws), `RetryChainFrom` and `ReplaceChain` hold the step while they work and roll back on failure, and `DeleteChain` keeps the chain and throws when a step it couldn't delete still runs; a recurring job whose schedule policy can't be evaluated (unreadable policy, unknown time zone, date provider missing or failing) stays scheduled and retries with an error, an `ExceptWhen` policy that can't be evaluated blocks, searches find the repeated hour of a daylight saving change, `Relaxed` catch-up checks the policy, `ScheduleOptions.WhenBlocked` without `Policy` throws, and policies are cached for about 5 seconds when jobs are created; `RepeatedFailuresMonitor` uses a sliding window and keeps an incident open until a success, paused monitors keep their incident, monitors registered after a server started are checked, `Alert` properties are init-only, webhooks require an absolute http or https URL, don't follow redirects, retry only transient failures (honouring `Retry-After`), and `Dispose` no longer waits for requests (`DisposeAsync` does); `nightshift.job.lateness` loses the recurring job tag (now on the `process` span) and records first runs only, `nightshift.job.stale_restarts` gains an outcome tag, continuations' lateness counts from when they became due, wrapped `TerminateJobException`s are honoured, arguments are compressed only at `CompatibilityLevel.Version_180`, and job log capture leaves out only the library's own categories (`ExcludeNightShiftCategories`); Redis prefixes must hold a hash tag (`AllowPrefixWithoutHashTag`) and Redis timing uses the server's clock, MongoDB needs 5.0 and commits with snapshot reads and majority writes on the server's clock, the EF Core storage checks column lengths before writing, records a schema version and refuses staging inside an open SQLite transaction, and a range read that ends before the first item reads nothing on every storage.
- More review fixes: a chain step runs only when its chain's record lists it (`JobChainStepFilter`, a new default global filter), so a chain whose creation stopped halfway, a deleted chain and the jobs a retry or a replacement replaced never run, a first step taken before the record lists it doesn't run until it does, and `Enqueue`, `Schedule` and `ReplaceChain` throw instead of returning a chain whose first step was lost; a chain that is being created, retried or replaced is told by a lease in its record, which the client renews while it works, not by the age of its jobs, so creating a chain has no time limit, no step starts during a change, and a `ReplaceChain` or `RetryChainFrom` whose process stops halfway leaves the chain as it was (the old chain runs when it was due, the step a retry held is put back into the state it was in); a chain's record is kept while a step is left to run or failed for good, and for 30 days after that, `RetryChainFrom` and `ReplaceChain` succeed once the new record is written and leave the jobs they couldn't delete to the next change of the chain or to a new server process, which also removes expired chains from the list and starts the waiting steps whose start was lost because a process stopped, a chain with a step about to start isn't settled, and a step put back after a failed retry isn't counted in the statistics again; a chain survives a deploy that renamed or removed a step's method (`GetChain` gives that step a `null` `Job`, the chain can still be deleted, settled and continued, and `RetryChainFrom` refuses only when it must create such a step again), a recurring occurrence creates its chain once (the chain's identifier comes from the job that creates it, so that job run again returns the same chain), a chain whose creation stopped halfway never runs, however far ahead its first step was scheduled (without a record, a job counts as a step of a chain whose record expired only when it carries the new `ChainRecorded` job parameter), a client that stalled past its 2-minute lease is told (`Enqueue`, `Schedule`, `ReplaceChain` and `RetryChainFrom` take the change back and throw) instead of leaving a chain with a deleted step, and a step whose start was lost is looked for every 15 minutes at most while its chain still runs; `UseDeploymentFencing(deploymentId, deploymentOrder)` lets a deployment order decide which deployment is newer (`DeploymentFencing.DeploymentOrder`, `GetCurrentDeploymentOrder`), so with orders a stray instance of an old build no longer fences the current servers, a deployment id has one order (the highest its servers were started with), and whether a deployment is alive is told by watching its sign of life change with each server's own clock, so the servers' clocks needn't be synchronized, and only while the watching server itself was checking, so after a storage outage a fenced deployment doesn't take over from a live one; a fire-and-forget or delayed job whose schedule policy can't be evaluated is never skipped or rejected, and creating it never throws: it waits in the Scheduled state and is checked again after 1, 5 and 15 minutes, then every hour (`PolicyCheckAttempts` job parameter), `MoveForward` moves a blocked job to the first instant the policy can't evaluate instead of reporting no time in ten years, and registering an unchanged recurring job again keeps one that waits for its policy where it is; disposing a distributed lock of the Entity Framework Core, Redis, MongoDB and in-memory storages no longer waits for a renewal in progress.
- Further review fixes: the SQL Server storage sets job parameters inside a write transaction (`JobStorageFeatures.Transaction.SetJobParameter`), so a chain's `ChainRecorded` marks commit with the chain's record (a step is never listed without its mark, and a record that fails to commit leaves none) and the `Lease`, `StaleRestarts`, cleared `HeldQueue`, `DueAt` and `ScheduledFor` job parameters with the state change they belong to, as on the other storages, a parameter written in a transaction for a job that doesn't exist is ignored on every storage while the rest of the transaction commits, and with `AllowDelayedDurability` a transaction that writes a job parameter always waits for the disk; the Entity Framework Core storage reads the database's clock on SQL Server, PostgreSQL, MySQL, MariaDB and Oracle (`EntityFrameworkCoreStorageOptions.DatabaseClockSql` for another provider, or to replace a built-in statement), so the schedulers, the dashboard, the health endpoints, the chain lease and server heartbeats go by one clock there and `UseTimeProvider` no longer drives the schedulers, SQLite keeps the process's clock, and a statement that fails its check at first use is logged once and leaves the process on its own clock; `/health`, `/metrics` and the ASP.NET Core health check compare server heartbeats and late recurring jobs with the storage's clock where the storage has one, at the cost of one clock read per request, so a process whose clock is ahead no longer reports that no server is alive, and the MongoDB storage writes and times out server heartbeats with MongoDB's clock; a server with `UseDeploymentFencing` takes no job before its first deployment check has succeeded, and a fenced server whose own checks keep coming more than one and a half check intervals apart, so that it can never take over, logs a warning that says so; a job skipped by `SkipAfter` or `[SkipIfLate]` after it waited for a schedule policy that couldn't be evaluated names the policy in its reason (`Skipped: started 3 h late: waited for policy '...', which couldn't be evaluated`) and in a warning, as does a run of a recurring job that was due while the recurring job waited (the new `WaitedForPolicy` job parameter), and `PolicyCheckAttempts` is set to `0`, not removed, once the policy lets the job run; a chain stays in the list, with its flowchart, while the job of a step exists in a state other than Succeeded or Deleted, so a failed chain is kept for as long as its failed job is, a finished chain is kept for the new `UseChainRetention` setting (30 days by default, `JobChain.RecordRetention` is now a property) and the `ChainRecorded` job parameter holds the writer's retention in seconds, chain maintenance reads only the chains that are due for a look (the `chains:due`, `chains:expiring` and `chains:soon` sets replace `chains:joins`, and chains listed by earlier builds are taken in 500 a run through `chains:index`), looks at every chain with more than one step, and starts a continuation that was never told its parent finished with the parent's result or exception under `UseResultsInContinuations`, a first step that a worker takes while its chain is being created is given back to its queue without a state change or a history entry and taken again a moment later (the `Waiting for chain ... to be recorded` entries appear only when the creation takes more than 5 seconds or its client stopped), and `RetryChainFrom` holds its step for 2 minutes 15 seconds instead of 5 minutes, no longer fails because preparing the retry outlasted the hold, puts a step back with the expiry it had when the retry fails, and, when the retrying process stops or stalls past its lease before the retry is recorded, no longer lets the step run: a server puts it back into the state it was in (reason `The retry of chain ... was abandoned`, no `Processing` entry, no automatic retry, alert, monitor outcome, statistics count or activity feed entry) and deletes the jobs the retry had created; concurrent job creation on SQL Server no longer deadlocks (error 1205) when the `Job` table is empty or very small, as right after a first start or a purge.
- A third review added `BatchJob.Cancel`/`RequeueFailed`, `JobStorage.RequeueFailedJobs`, `GetJobState`, `TryGetResult<T>`, `ThrottleAttribute.GetSlots`/`Release`, repeatable `[RateLimit]` for tiered limits, a page on job progress, console and checkpoints, and fixed, among others: Hangfire-stored collection arguments that couldn't be read after the migration, structs losing their values, a fetched job that could stay invisible after a connection drop, succeeded jobs failed by a storage error while releasing a throttle slot or writing a console line, `tonight at 9` meaning 09:00, recurring runs lost when enqueuing one failed, the dashboard's catalog form and live polling, and the Prometheus family name clash.
- A second review fixed, among others: job arguments losing members equal to their `[DefaultValue]`, job payloads unreadable under a snake_case naming policy, the dashboard's Pause buttons, same-named job types sharing concurrency slots, the circuit breaker counting lock timeouts, SQL Server installs with non-Latin schema names, servers listening to 64 or more queues, and the packed MSBuild props file being ignored by git. See `docs/changes-from-hangfire.md`.
